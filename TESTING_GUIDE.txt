================================================================================
  SECTION 1 — HOW TO START THE PROJECT
================================================================================

  Prerequisites
  ─────────────
  - Java JDK 21+ installed
  - Maven 3.8+ installed
  - A terminal (Command Prompt, PowerShell, or IntelliJ terminal)

  Step 1: Start the Backend
  ─────────────────────────
  1. Open a terminal.
  2. Navigate to the backend folder:
       cd backend
  3. Run the Spring Boot backend:
       mvn spring-boot:run
  4. Wait for the console output to show:
       "Started CleMediceApplication in XX.XXX seconds"
       "=== Seed complete: 20 patients, 5 users, 10 rdv, 4 paiements ==="
     This means the database has been initialised with test data.

  Step 2: Verify Backend is Running
  ──────────────────────────────────
  1. Open a web browser.
  2. Go to: http://localhost:8080/h2-console
  3. On the login page, enter:
       JDBC URL: jdbc:h2:file:./data/clemedice
       Username: sa
       Password: (leave empty)
  4. Click Connect.
  5. If you see the H2 database console with tables listed (PATIENTS, USERS,
     RENDEZ_VOUS, CONSULTATION_DETAILS, ORDONNANCE, MEDICAMENT, PAIEMENTS),
     the backend is running correctly.

  Step 3: Start the Frontend
  ───────────────────────────
  1. Open a SECOND terminal (keep the backend terminal running).
  2. Navigate to the frontend folder:
       cd frontend
  3. Run the JavaFX application:
       mvn javafx:run
  4. Wait for the JavaFX window to open (may take 10-30 seconds on first run).

  Step 4: What to Expect on Screen
  ─────────────────────────────────
  - A login window appears with:
    - "CleMedice" title
    - Email field
    - Password field
    - "Se connecter" button
  - Background has the application's styled colour scheme.
  - If the login window appears, the frontend is connected and ready.


================================================================================
  SECTION 2 — HOW TO RUN THE UNIT TESTS
================================================================================

  Step 1: Stop the Backend (important)
  ─────────────────────────────────────
  The integration tests need to start their own embedded server. If the backend
  is already running on port 8080, the tests will fail with "address already in
  use". Close the backend terminal, or press Ctrl+C in the backend terminal.

  Step 2: Run All Tests
  ─────────────────────
  1. In a terminal, navigate to the backend folder:
       cd backend
  2. Run the tests:
       mvn test
  3. Maven will compile test classes and execute them.

  What Each Test Class Tests
  ──────────────────────────

  A) PatientServiceTest (6 tests)
     Location: backend/src/test/java/com/cabinet/service/PatientServiceTest.java
     Tests the PatientService business logic in isolation using Mockito.
     Repository calls are mocked — no real database is used.
     Tests include: listing all patients, finding by ID, handling "not found",
     creating a patient, deleting a patient, and searching by keyword.

  B) DocumentFactoryTest (5 tests)
     Location: backend/src/test/java/com/cabinet/factory/DocumentFactoryTest.java
     Tests the Factory design pattern implementation.
     Verifies that each DocumentType (ORDONNANCE, ATTESTATION,
     CERTIFICAT_ARRET_TRAVAIL, CERTIFICAT_APTITUDE) produces a document map
     with the correct keys and header text. Also verifies that every document
     always contains a non-empty date field.

  C) SingletonPatternTest (2 tests)
     Location: backend/src/test/java/com/cabinet/factory/SingletonPatternTest.java
     Demonstrates the Singleton concept by proving that calling
     DocumentFactory.createDocument() with identical inputs produces
     consistent output. Also verifies all four document types are creatable
     without throwing exceptions.

  D) PatientControllerIntegrationTest (5 tests)
     Location: backend/src/test/java/com/cabinet/controller/
               PatientControllerIntegrationTest.java
     Tests real HTTP endpoints against an embedded Spring Boot server with an
     in-memory H2 database. Tests include: GET /api/patients with and without
     authentication, POST /api/patients to create a new patient,
     GET /api/patients/search, and login with wrong password returning 401.

  What a PASS Looks Like
  ──────────────────────
  At the end of the test run, you will see:

      [INFO] Results:
      [INFO]
      [INFO] Tests run: 18, Failures: 0, Errors: 0, Skipped: 0
      [INFO]
      [INFO] -----------------------------------------------------------------
      [INFO] BUILD SUCCESS
      [INFO] -----------------------------------------------------------------

  The number "18" is the total test count. All tests must show 0 Failures and
  0 Errors for a clean pass.

  What a FAIL Looks Like
  ──────────────────────
  A failure will show:

      [INFO] Tests run: 18, Failures: 1, Errors: 0, Skipped: 0
      [INFO]
      [INFO] -----------------------------------------------------------------
      [INFO] BUILD FAILURE
      [INFO] -----------------------------------------------------------------

  A detailed stack trace will appear showing which test method failed and at
  which assertion. Check:
    - Is the backend already running on port 8080?
    - Are the test source files in the correct packages?
    - Does DocumentFactory.java exist in backend/src/main/java/com/cabinet/factory/?
    - Are there any import errors in the test files?

================================================================================
  SECTION 11 — TESTING DESIGN PATTERNS (FOR ACADEMIC REPORT)
================================================================================

  A) Singleton Pattern — AppConfig
  ──────────────────────────────────
  File: frontend/src/main/java/com/cabinet/ui/config/AppConfig.java

  How to demonstrate:
    1. Open AppConfig.java in your IDE.
    2. Observe that the constructor is private:
         private AppConfig() {}
    3. Observe the getInstance() method uses double-checked locking:
         if (instance == null) {
             synchronized (AppConfig.class) {
                 if (instance == null) {
                     instance = new AppConfig();
                 }
             }
         }
    4. This ensures only ONE AppConfig object ever exists in the entire
       application, even if multiple threads call getInstance() at once.

  To verify at runtime:
    - Call AppConfig.getInstance() twice and compare the references:
        AppConfig c1 = AppConfig.getInstance();
        AppConfig c2 = AppConfig.getInstance();
        // c1 == c2 is always true
    - SingletonPatternTest in the backend also demonstrates a similar
      consistency concept for DocumentFactory.

  B) Builder Pattern — RendezVousRequest
  ────────────────────────────────────────
  File: frontend/src/main/java/com/cabinet/ui/model/RendezVousRequest.java

  How to demonstrate:
    1. Open RendezVousRequest.java in your IDE.
    2. Show the fluent Builder inner class with its chainable setter methods.
    3. The typical usage pattern:
         RendezVousRequest request = new RendezVousRequest.Builder()
             .patientId(1L)
             .medecinId(1L)
             .date(LocalDate.now())
             .heure(LocalTime.of(9, 0))
             .topic("Controle de routine")
             .build();
    4. Show that calling build() without mandatory fields throws an exception:
         new RendezVousRequest.Builder()
             .patientId(1L)
             .build()
         // Throws IllegalStateException: "medecinId is required"
    5. The Builder pattern separates object construction from the object's
       representation. The RendezVousRequest constructor is private, so the
       only way to create an instance is through the Builder.

  C) Factory Pattern — DocumentFactory
  ──────────────────────────────────────
  File: backend/src/main/java/com/cabinet/factory/DocumentFactory.java

  How to demonstrate:
    1. Open DocumentFactory.java in your IDE.
    2. Show the createDocument() method that takes a DocumentType enum plus
       patient details and returns a Map<String, String>.
    3. The switch statement chooses the correct document structure:
         - ORDONNANCE        → titre "Ordonnance Medicale"
         - ATTESTATION       → titre "Attestation Medicale"
         - CERTIFICAT_ARRET  → titre "Certificat d'Arret de Travail"
         - CERTIFICAT_APTITUDE → titre "Certificat d'Aptitude"
    4. The caller does NOT need to know how each document type is constructed.
       It simply provides the type and the data, and the factory handles the
       creation logic.
    5. Run the tests:
         cd backend
         mvn test -Dtest=DocumentFactoryTest
    6. All 5 tests should pass, proving:
         - Ordonnance has correct type "ORDONNANCE"
         - Attestation has correct type "ATTESTATION"
         - Arret de Travail has correct type "ARRET_TRAVAIL"
         - Certificat d'Aptitude has correct type "APTITUDE"
         - Every document includes a date field


================================================================================
  SECTION 12 — VERIFYING DATA IN H2 CONSOLE
================================================================================

  The H2 database console provides direct SQL access to the database.

  Step 1: Open the Console
  ─────────────────────────
  1. With the backend running, open a browser.
  2. Go to: http://localhost:8080/h2-console
  3. Enter:
         JDBC URL:  jdbc:h2:file:./data/clemedice
         Username:  sa
         Password:  (leave empty)
  4. Click "Connect".

  Step 2: Run SQL Queries
  ────────────────────────
  Copy and paste each query into the SQL editor, then click "Run".

  Query 1 — List all patients:
      SELECT id, nom, prenom, cin FROM patients ORDER BY id;
    Expected: 20 rows with patients (Najim, Adil, Saad, Houssam, Mohsin, etc.)

  Query 2 — List all users:
      SELECT id, nom, email, role, enabled FROM users ORDER BY id;
    Expected: 5 rows with admin, najim, adil, saad, houssam.
              admin has role "MEDECIN_PRINCIPAL".

  Query 3 — List all rendez-vous with patient names:
      SELECT r.id, p.nom, p.prenom, r.date, r.heure, r.statut
      FROM rendez_vous r
      JOIN patients p ON r.patient_id = p.id
      ORDER BY r.date;
    Expected: 10 rows with various dates, statuses (PLANIFIE, EFFECTUE, ANNULE).

  Query 4 — List all payments:

  Error: "Connection refused" when navigating any screen
  ────────────────────────────────────────────────────────────────────────
  Cause: The backend Spring Boot application is not running.
  Fix: Open a terminal, navigate to the backend folder, and run:
         mvn spring-boot:run
       Wait for the "Started CleMediceApplication" message before using the
       frontend.

  Error: Login fails with "Identifiants incorrects" but credentials are correct
  ────────────────────────────────────────────────────────────────────────
  Cause: The backend may have restarted and lost the H2 data file, or the
         DataInitializer did not run because the database already existed
         from a prior run.
  Fix: Check if backend/data/clemedice.mv.db exists. Delete it, restart the
       backend with "mvn spring-boot:run", and verify the seed message
       appears in the console.

  Error: PDF does not open after clicking "Generer PDF"
  ────────────────────────────────────────────────────────────────────────
  Cause: No default PDF viewer is configured on the system, or the file was
         generated but could not be opened.
  Fix:
    1. Check your system temp folder:
         C:\Users\HP\AppData\Local\Temp
    2. Look for files named "ordonnance_X_.pdf" or "attestation_.pdf".
    3. If the files exist, open them manually with Adobe Acrobat or Edge.
    4. If they do not exist, check the backend console for any error stack
       trace related to iText PDF generation.

  Error: Table is empty after login
  ────────────────────────────────────────────────────────────────────────
  Cause: DataInitializer did not seed the database.
  Fix: Look at the backend terminal output. Do you see the line:
         "=== Seed complete: 20 patients, 5 users, 10 rdv, 4 paiements ==="
       If not, stop the backend, delete the file "backend/data/clemedice.mv.db"
       and any "clemedice.trace.db" files, then restart the backend.

  Error: mvn test fails with "Application context failed to load"
  ────────────────────────────────────────────────────────────────────────
  Cause: The backend is still running on port 8080 when tests start. The
         integration tests attempt to start their own embedded server but
         the port is already taken.
  Fix: Stop the backend (Ctrl+C in the backend terminal or kill the Java
       process). Then run "mvn test" again.

  Error: mvn test BUILD FAILURE with "cannot find symbol"
  ────────────────────────────────────────────────────────────────────────
  Cause: A required source file is missing or in the wrong package.
  Fix: Verify that the following files exist in the correct locations:
         - DocumentFactory.java
             backend/src/main/java/com/cabinet/factory/DocumentFactory.java
         - DocumentFactoryTest.java
             backend/src/test/java/com/cabinet/factory/DocumentFactoryTest.java
         - PatientServiceTest.java
             backend/src/test/java/com/cabinet/service/PatientServiceTest.java
         - SingletonPatternTest.java
             backend/src/test/java/com/cabinet/factory/SingletonPatternTest.java
         - PatientControllerIntegrationTest.java
             backend/src/test/java/com/cabinet/controller/
               PatientControllerIntegrationTest.java

  Error: mvn javafx:run fails with "JavaFX runtime components missing"
  ────────────────────────────────────────────────────────────────────────
  Cause: The system PATH may not include JavaFX modules.
  Fix: Run the frontend using the Maven wrapper which includes all required
       plugins:
         cd frontend
         mvn clean javafx:run
       If it still fails, verify that pom.xml contains the JavaFX Maven plugin
       configuration (javafx-maven-plugin) and that Java 17+ is set.

  Error: "Database may be already in use" when starting backend
  ────────────────────────────────────────────────────────────────────────
  Cause: A previously killed Java process still holds the H2 lock file.
  Fix: In PowerShell (as Administrator), run:
         Stop-Process -Name "java" -Force
       Then restart the backend with "mvn spring-boot:run".
